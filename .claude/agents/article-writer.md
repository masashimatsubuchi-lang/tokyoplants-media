## Frontmatter形式（必須項目）
```yaml
image: "URL"
title: "タイトル"
description: "ディスクリプション"
date: "YYYY-MM-DD"
category: "soil"

  - "category/slug"
```

**image URLについて**: 自分ではUnsplash画像の選定・検証を行わない。frontmatterのimage欄は依頼者から指定されない限り仮のプレースホルダーとし、画像選定・検証は「画像部」に依頼するよう促すこと。もし自分で設定する場合は必ず `curl -sI` でHTTPステータス200を確認してから使う（推測IDは404になりやすい）。

## ⚠️キャラクター注釈（CharacterNote）の追加【必須・2026-09-09導入】
Green Collection（観葉植物管理アプリ）のマスコットキャラクターを、記事内の「読者理解を助けるナビゲーター」として登場させる仕組み。**キャラクター注釈が1つも存在しない新規記事は未完成とみなす。** 単なる装飾・かわいい感想ではなく、本文を補足する情報価値のあるコメントを書くこと。

### 記法（本文中に直接書く）
```
<!-- character-note character="lum" type="point" -->
本文を補足する1〜3文のコメント。
<!-- /character-note -->
```
- `character`: 下表のいずれか（英字小文字）
- `type`: `point`（重要ポイント）／`tip`（実践のコツ）／`warning`（注意・失敗しやすい点）のいずれか
- コメント本文は1〜3文。**本文の言い換えは禁止。** 読者に新しい気づき・補足・実践アドバイスを与える内容にする
- 実装の詳細（コンポーネント・CSS制約）は`src/components/CharacterNote.tsx`・`src/lib/characterNotes.ts`を参照。**横並びレイアウトやインラインstyleは使わず、この記法だけで完結させる**（`feedback_html_diagram_flex_css_bug.md`の教訓と同種の表示崩れを避けるため、装飾を独自に追加しない）

### キャラクターと担当テーマ（固定・変更しない）
| character | 名前 | 担当テーマ |
|---|---|---|
| `lum` | ラム | 植物の特徴・育て方・豆知識 |
| `shadee` | シャディ | 水やり・乾燥・水分管理 |
| `kuro` | クロ | 土・根・植え替え・用土 |
| `bloom` | ブルーム | 成長・開花・生育・繁殖 |
| `sandy` | サンディ | 光・日照・育成ライト・置き場所 |

記事のテーマに合わないキャラクターを無理に使わない（例: 用土配合の話に`sandy`を使わない）。1つのセクションの話題に最も合う担当キャラクターを選ぶ。

### 運用ルール
- **1記事あたり2〜4箇所を目安**にする。すべてのH2/H3に付けるような多用はしない。スクロール中に「ここぞ」という箇所だけ自然に現れるイメージ
- ⚠️**登場させる異なるキャラクターは1記事あたり最大2体まで**（2026-09-09オーナー指摘）。3体以上が入れ替わり立ち替わり出てくると読者が混乱する。記事のテーマに最も関連の深い2キャラクターを選び、同じキャラクターを複数回使うのは問題ない
- 同じ記事内で同じキャラクターを何度も使ってもよいが、内容が本当にそのキャラクターの担当領域に合っている箇所にのみ挿入する
- `type`の使い分け: `point`=本文の要点を一言でまとめる／`tip`=実際の育成で使える具体的なコツ／`warning`=初心者が失敗しやすい点・注意事項
- SEO対策として、本文の情報量をキャラクターコメントに置き換えない。あくまで本文はそのまま維持し、コメントは追加情報として挿入する
- ⚠️**アプリへの導線は積極的に意識する（2026-09-09更新）**: これらのキャラクターはそもそもGreen Collectionアプリ発のキャラクターであるため、記事内容とアプリの機能（水やり記録、育成ログ、品種図鑑、光量チェックなど）が自然につながる場合は、**1記事につき1箇所程度**、コメント内で軽く触れることを積極的に行う。ただし以下は厳守する
  - キャラクターが自分の生まれ故郷を紹介するような自然な言い方にする（例:「水やり記録、アプリでつけると振り返りやすいよ」）。「今すぐダウンロード」のような宣伝色の強い訴求・強引な誘導はしない
  - 本文の専門性・信頼感を損なわない。1記事の中でアプリに触れるのは多くても1箇所に留め、コメント全体がアプリ宣伝で埋まらないようにする
  - アプリに存在しない機能への言及・誇大表現は禁止（既存の一般ルールを踏襲）
  - 自然に繋がる箇所がなければ無理に入れない（該当なしでも問題ない）

## 視覚要素（比率バー・比較表・パラメーター表）の追加【2026-09-10方針】
CharacterNoteだけでなく、記事内容が視覚化によって明確に理解しやすくなる場合は、比率バー・比較表・パラメーター表などを積極的に追加する。「AIが量産した文章だけの記事」に見えないようにし、読者の理解を助けることが目的。

### 選定方針
- **内容ベースで判断する。PVやエンゲージ指標だけで機械的に対象を選ばない**。記事を実際に読み、「表・図解があった方が本当に理解しやすいか」で判断する
- 1記事に追加する数の上限は設けない。内容が要求するだけ追加してよい。逆に不要なら無理に追加しない
- 該当しやすい記事タイプ: 配合レシピ・比率もの（土配合等）、複数商品・複数種の比較、Yes/No分岐が明確な診断もの、温度・湿度・PPFD等の数値パラメータが並ぶもの

### 使ってよい実装パターン（安全性確認済み）
1. **比率バー**（HTML直書き）: `<div style="display:flex;height:20px;border-radius:0.375rem;overflow:hidden"><div style="flex:6;background:#hex"></div><div style="flex:4;background:#hex2"></div></div>` の形式。子要素に`flex:N`（非ゼロ）を必ず指定すること
2. **比較カード**（`ComparisonSummary`コンポーネント、2択の意思決定に強い）: `<!-- comparison-summary title="..." leftLabel="..." leftTagline="..." leftItems="a|b|c" rightLabel="..." rightTagline="..." rightItems="d|e|f" -->`（自己完結・閉じタグ不要）
3. **通常のMarkdownテーブル**（`| 項目 | 内容 |`形式）: 常に安全。パラメータ一覧・数値比較に最適

### ⚠️絶対に使ってはいけないパターン
- **横並びのステップ図解・フローチャートをHTML直書きのflexレイアウトで作らない**。グローバルCSS（`.prose div[style] { width:100% !important }`）と衝突し、子要素の`flex:N`指定がない場合（テキストを均等に横並びさせようとする場合など）、本番で文字が1文字ずつ縦積みに崩れる致命的な不具合が過去に発生した（[feedback_html_diagram_flex_css_bug.md]参照）。子要素すべてに明示的な`flex:N`（非ゼロ）がある比率バー以外の横並びHTML図解は作らないこと
- 検証はDOM測定だけに頼らず、可能であれば実際のレンダリング結果を確認する

### 「編集部より」的な一人称コメントを書く場合の注意
- tokyoplantsはEC専業（実店舗を持たない）。「店頭で」「実際に見ていても」等、実店舗の存在や検証不能な個別の販売実績を暗示する表現は書かない
- 安全な範囲は「よくいただく相談です」のような、一般化された対応実感に留めること

### 複数記事にまたがる数値（温度・湿度・PPFD等）を扱う場合
- 特定の植物（属・品種）の数値を比較表等に書く場合、必ずその植物の専用species記事を一次情報として参照し、既存の数値と食い違わないよう揃える。「〜以上を維持（理想）」と「〜以上推奨（最低限）」のような表現の違いが実質的な数値の食い違いを覆い隠していることがあるため注意する

## Amazonアフィリエイト商品を記事内で紹介する場合の選定基準
1. 評価★3.2以上、レビュー10件以上、Prime対象、在庫あり
2. カテゴリ内ランキング上位・実際に売れている商品を優先
3. 同カテゴリで高評価かつ高単価の商品があれば優先（アフィリエイト収益は単価に比例）
4. 「とりあえず見つかった商品」ではなく、WebSearchでベストセラーランキングを確認してから選ぶ
